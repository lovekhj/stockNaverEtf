# 실시간 감시 · 성과 추적 · 예측 시스템 설계 명세서

> 최종 수정: 2026-10-09

## 1. 개요 및 목적

매일 장 마감 후 생성되는 `reports/report_YYYYMMDD.csv`(약 500개 주도주 후보)를 **감시 대상을 고르는 소스**로 사용하고, 증권사 API로 **장중 실시간 감시**를 수행합니다. 동시에 선정 종목의 **이후 성과를 매일 누적 기록**하여, 거래량·차트 특징과 성과의 관계를 통계로 쌓고 새로 만나는 종목의 결과를 예측하는 것을 목표로 합니다.

| 구분 | 역할 | 실행 시점 |
|------|------|-----------|
| 일일 분석 (`main.py`) | 후보 종목 분석 → 다음 날 감시 대상 확정, 특징(feature) 저장 | 매일 16:00 이후 |
| 실시간 감시 (`monitor.py`) | 증권사 WebSocket 체결가 구독 → 조건 판정 → 텔레그램 알림 | 08:50 ~ 15:30 |
| 성과 추적 | 과거 선정 종목의 T+1 / T+5 등 결과(label) 채우기, 성적표 생성 | 매일 16:00 이후 |
| 웹 대시보드 | 결과 조회 전용 (판정 로직 없음) | 상시 |

---

## 2. 감시 대상 정의

CSV 전체(약 500종목)를 실시간으로 감시하지 않습니다. 대상은 두 종류로 좁힙니다.

### 1) 매수 후보 (watchlist)
- 출처: 당일 CSV + 대시보드 기본 필터 (**A등급 / 망치형·아래꼬리 / 적정**) → 보통 5~15종목
- 알림 조건:
  - 현재가가 CSV의 `추천매수가` 구간에 진입 → **진입 알림**
  - 20일 이격도 108% 초과 → **추격 금지 알림**

### 2) 보유 종목 (holdings)
- 출처: 실제 매수 이력 (`holdings` 테이블)
- 알림 조건: 아래 3장의 손절 규칙

감시 종목 수가 적어서 증권사 WebSocket 구독 한도 안에서 충분히 운영할 수 있습니다.

## 3. 손절 감지 3대 핵심 알고리즘

### 1) 매수가 대비 -3% 절대 손절선 (원금 보전 철칙)
* **공식**: `((실시간 현재가 - 1차 매수가) / 1차 매수가) * 100 <= -3.0%`
* **작동**: 매수 진입 후 주가가 -3% 떨어지면 즉시 손절 경고 발송.
* **효과**: 판단 오류 시에도 전체 원금 대비 손실을 **-1.2% 이내로 엄격히 통제**.

### 2) 전일 종가 대비 -3% 갭하락 손절선 (장중 변동성 방어)
* **공식**: `((실시간 현재가 - 어제 종가) / 어제 종가) * 100 <= -3.0%`
* **작동**: 장 시작 후 기습적인 음봉 급락이나 악재로 전일 종가 대비 -3% 이상 밀릴 때 매도 경고.

### 3) 2차 매수(불타기) 후 본전 방어 스탑로스
* **공식**: `2차 매수 완료 후 실시간 현재가 <= 1차 매수가 (본전)`
* **작동**: 주가가 +3%~+5% 상승하여 2차 매수(30%)를 마친 후, 주가가 다시 꺾여 1차 매수가로 복귀하면 **손실금액 0원(본전)에서 즉시 전량 매도**.

### 알림 중복 방지
가격이 -3% 선 근처에서 오르내리면 알림이 반복됩니다. **종목·조건별로 하루 1회만 보내거나 일정 시간 동안 재알림을 막습니다.**

## 4. 시스템 아키텍처 (Mac mini 단독 운영)

```text
Mac mini (상시 가동)
 ├─ main.py           매일 16시 이후 분석 → 감시 대상 확정 + 특징 저장 + 지난 결과 채우기
 ├─ monitor.py        08:50~15:30, KIS WebSocket으로 감시 → 텔레그램 알림 + DB 저장
 ├─ 로컬 웹 서버       index.html 제공 + /api (시세·알림·성적표 조회)
 │   (FastAPI/Flask)   증권사 API 키는 이 서버의 .env에만 보관
 └─ SQLite            features / outcomes / holdings / alerts / 시세 스냅샷
        ▲
   브라우저 http://localhost:8000   (외부에서 볼 때는 Tailscale)
```

### 설계 원칙
1. **판정 로직은 브라우저가 아니라 Python(`monitor.py`)에 둔다.**
   브라우저 탭이 백그라운드로 가거나 화면이 잠기면 Chrome이 타이머를 크게 늦춥니다(숨겨진 탭은 약 1분 간격). 손절 판정을 `app.js`에서 하면 알림을 놓칠 수 있습니다. 웹 화면은 결과 표시만 합니다.
2. **API 키는 프론트엔드 파일에 절대 넣지 않는다.**
   이 저장소는 GitHub에 push되고 GitHub Pages로 공개됩니다. 키는 `.env`(gitignore 처리됨)에만 두고, 서버 코드만 읽습니다.
3. **체결가를 받는 대로 전부 저장하지 않는다.** 알림과 1분 단위 스냅샷만 저장합니다.

### Mac mini 운영 체크리스트
- 시스템 설정: 자동 잠자기 방지, 정전 후 자동 시작 (디스플레이 꺼짐은 무관)
- `monitor.py`와 웹 서버는 **launchd**로 등록 (재부팅 후 자동 재실행, 장 시간에 맞춘 시작·종료)
- 네트워크 끊김에 대비한 **WebSocket 자동 재접속** 로직 필수
- 외부(휴대폰) 조회는 공유기 포트 개방 대신 **Tailscale** 사용
- 급한 알림은 텔레그램으로 받으므로, 웹 화면은 집에서만 봐도 충분

### SQLite vs Supabase
| 상황 | 선택 |
|------|------|
| Mac mini에서 조회 + 외부에서는 텔레그램 알림만 | **SQLite** (충분) |
| GitHub Pages 대시보드를 어디서든 열고 싶음 | Supabase |
| Mac mini가 꺼져 있어도 과거 리포트를 보고 싶음 | Supabase |
| Tailscale 없이 휴대폰에서 보고 싶음 | Supabase |

Supabase를 쓸 경우:
- RLS(행 수준 보안)를 켜고 anon 키에는 **SELECT만** 허용합니다. 쓰기는 Python에서 service_role 키로만 합니다.
- 브라우저 알림은 Supabase Realtime 구독으로 받습니다.
- 대시보드는 Supabase를 먼저 읽고, 실패하면 CSV로 대체 조회합니다.

처음에는 SQLite로 시작하고, 필요해지면 그때 Supabase로 옮깁니다.

## 5. 증권사 실시간 API

| 증권사 | 방식 | Mac 지원 | 비고 |
|--------|------|----------|------|
| **한국투자증권 KIS Developers** | REST + WebSocket | O | 모의투자 지원, 예제·자료 가장 많음 → **1순위** |
| 키움 | OpenAPI+ (Windows 전용) / 신규 REST API | REST만 가능 | REST는 자료가 상대적으로 적음 |
| LS증권 Open API | REST | O | 대안 |

### 운영 시 주의
- **접근 토큰**: 유효기간과 발급 횟수 제한이 있으므로 매 실행마다 새로 받지 말고 파일/DB에 저장해 재사용합니다.
- **호출 제한**: REST 초당 호출 수, WebSocket 구독 종목 수에 제한이 있습니다(정확한 수치는 KIS 공식 문서 확인, 모의투자는 더 낮음). 실시간 시세는 WebSocket, REST는 전일 종가 같은 보조 조회에만 사용합니다.
- **네이버 시세 API(`m.stock.naver.com`)**: 비공식 API이고 1~3분씩 늦어서 손절 알림 용도로는 부족합니다. 초기 프로토타입에만 사용합니다.
- **자동 주문은 마지막 단계**: 알림 전용으로 시작하고, 주문 기능은 모의투자로 충분히 검증한 뒤 붙입니다.

## 6. 선정 종목 성과 추적 및 예측

### ⚠️ 선행 과제: 현재 캔들 데이터는 실제 데이터가 아님
CSV에는 캔들/차트꼬리 컬럼이 없습니다. 그래서 `app.js`의 `loadDashboardData`가 **종목코드 홀짝(`codeNum % 2`, `codeNum % 3`)으로 캔들 형태를 임의로 만들어** 화면에 표시합니다. 즉 현재의 "망치형·아래꼬리" 필터는 사실상 무작위 조건입니다.

→ **실제 일봉 OHLCV(시가·고가·저가·종가·거래량)를 수집해 캔들을 계산하는 것이 모든 분석의 첫 단계**입니다. 거래량 분석에도 같은 데이터가 필요합니다.

### 데이터 흐름

```text
[T일 장 마감 후] 특징(feature) 스냅샷          [T+N일 후] 결과(label) 채우기
  - 등급, 수급, 이평선, 이격도 (현재 CSV)        - T+1 시가 갭, T+1 종가 수익률
  - 실제 캔들: 몸통/윗꼬리/아랫꼬리 비율         - T+3, T+5, T+10 수익률
  - 거래량: 20일 평균 대비 배수                 - 기간 내 최고가/최저가
  - 갭, 변동성(ATR), 52주 고점 대비 위치         - "+5% 먼저 vs -3% 먼저" 도달 여부
                    │                                    │
                    └────────► (date, code) 기준 결합 ◄────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
       매일 성적표 리포트           조건별 누적 통계               예측 모델
   "어제 선정 종목 → 오늘 결과"   등급×캔들×과열×거래량별 승률    (데이터 축적 후)
```

### 테이블 설계 (초안)
- `features(date, code, name, sector, grade, dual_buy, foreign_streak, inst_streak, ma5, ma20, ma60, ma120, disparity_20, overheat, candle_body, upper_wick, lower_wick, volume_ratio_20, gap, atr, ...)`
- `outcomes(date, code, entry_price, ret_1d, ret_3d, ret_5d, ret_10d, max_high_10d, min_low_10d, hit_up5_first, ...)`
- `holdings(code, name, buy_price, quantity, buy_date, pyramid_step, status, ...)`
- `alerts(ts, code, rule, price, message)`
- CSV의 표시용 문자열(`"94,900"`, `"+2.04%"`, `"O"/"X"`)은 DB에 **숫자/boolean 타입으로 변환**해 저장합니다(`--3.22%` 같은 잘못된 값도 이때 정리). 컬럼명은 영문으로 하고 Python에서 매핑합니다.

### 분석 원칙
1. **진입가는 실제로 체결할 수 있는 가격으로 잡는다.**
   리포트는 장 마감 후 나오므로 T일 종가로는 살 수 없습니다. 기본은 **T+1 시가**이며, 오후 4시 시간외 단일가 전략을 쓰는 경우 그 가격을 기준으로 합니다. (T일 종가 기준 = 미래 정보 사용, look-ahead bias)
2. **주 지표는 매매 규칙과 일치시킨다.**
   "다음 날 올랐나"만 보지 않고, **"N일 안에 +5%에 먼저 닿았나, -3%에 먼저 닿았나"**를 주 지표로 삼습니다. 실제 손익과 가장 가깝습니다.
3. **항상 기준선과 비교한다.**
   필터 종목의 승률은 같은 날 **전체 후보(약 500종목) 평균 및 KOSPI**와 나란히 보여줍니다.
4. **과거 데이터를 소급 계산해 표본을 확보한다.**
   `pykrx`(KRX 데이터, 무료)로 일봉 OHLCV와 투자자별 순매수 1~2년 치를 받아 특징·결과를 다시 계산합니다. 단, 과거 시점의 ETF 구성종목은 재현할 수 없으므로 **현재 종목 목록 기준이라는 한계(생존 편향)**를 기록해 둡니다.

### 예측 단계
- **1단계 — 조건별 통계표**: 예) "A등급 + 망치형 + 거래량 2배 이상 + 적정" → 5일 내 +5% 도달률, 표본 수, 평균 수익. 해석이 쉽고, 매수 우선순위 가이드(`stockDesc2.html`)를 실제 데이터로 검증하는 역할을 합니다.
- **2단계 — 모델**: 표본이 충분해지면 로지스틱 회귀 / LightGBM으로 "+5% 먼저 도달할 확률"을 계산합니다. 검증은 반드시 **날짜 순서대로 나누는 방식(walk-forward)**으로 합니다. 무작위로 섞어서 나누면 미래 정보가 섞여 성능이 부풀려집니다.
- **주의**:
  - 같은 날 종목들은 시장과 함께 움직이므로, 하루 500건이라도 독립 표본은 훨씬 적습니다.
  - 조건 조합을 많이 시험하면 우연히 좋아 보이는 조합이 반드시 나옵니다. **표본 30건 미만인 조건은 신뢰하지 않습니다.**
  - 거래비용(수수료·세금·슬리피지)을 수익률에서 차감합니다.

## 7. 포트폴리오 데이터 모델 (초기안: `data/my_portfolio.json`)

DB 도입 전 초기 단계에서 사용하는 JSON 구조입니다. DB 도입 후에는 `holdings` 테이블로 옮깁니다.

```json
[
  {
    "code": "008930",
    "name": "한미사이언스",
    "buyPrice": 53000,
    "quantity": 100,
    "buyDate": "2026-10-02",
    "stopLossPercent": -3.0,
    "targetProfitPercent": 15.0,
    "pyramidStep": 1,
    "status": "HOLDING"
  }
]
```

텔레그램 손절 알림 메시지 예시:
```text
🚨 [긴급 매도 손절 알림]
---------------------------------
- 종목명: 한미사이언스 (008930)
- 매수가격: 53,000원
- 현재가격: 51,400원 (수익률: -3.02%)
- 판단결과: 1차 손절선(-3%) 하향 이탈
---------------------------------
👉 즉시 전량 매도를 권장합니다!
```
